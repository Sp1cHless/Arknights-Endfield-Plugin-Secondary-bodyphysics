# PR #4 频率状态与停止收尾检查

日期：2026-10-17。检查对象为本地分支 `codex/apply-pr4-stop-tail`；本次没有安装到游戏目录。

## 频率拟合影响范围

自动拟合本来就共用于 walk、run、sprint 和 zipline。PR #4 合并版本 `a43532e` 中，采样器只在稳定循环上更新 `FreqLockState`，而 `SyntheticMotion` 在任意有效步态上直接使用最近一次的 `useHz`。因此，任何步态的起步/过渡阶段都可能使用上一种步态的拟合值；walk 是已有实机轨迹暴露该问题的场景。

先前的 `e9e32d6` 修复已经通过当前 gait 和配置频率检查拟合值归属，并在起步时选择当前步态自己的缓存或配置值，没有 walk 专用分支。

这次补充检查与修复：

- 64 组步态状态组合：四种源步态 × 四种目标步态 × 配置频率相同/不同 × 目标有缓存/无缓存。检查采样前的目标值、起步选择、手动频率开关、循环测量收敛。
- 稳定 loop 与过渡、pivot/bump、jump、idle、未知动画或其他步态混合时，单个高权重 loop 不能代表整个 Animator 状态的 normalizedTime。现在只有完整读取且全部属于同一步态的稳定 loop 才发布测量和相位参考。权重不作为排除其他可读动画的依据。
- 旧逻辑在时间停滞、无效、跳变或采样间隔过长时仍可能用旧 EMA 推进拟合。新增四项回归在修复前均失败，修复后通过。现在会清除连续偏差计数和测量有效性，同时禁止该次相位参考；持续停滞也不会循环重启旧参考。
- 20Hz 相位参考、20/30/60/144fps、不同起止频率的回放均满足 PLL 总修正界限。关闭相位对齐后只做自由频率积分。
- jump 映射为 Run 时仍被排除在 locomotion 测量外；跳跃输出使用独立控制器。Off/AmplifyNative 没有新增拟合输出或写入路径。角色切换与热重载保留原有状态重置和按角色/步态/配置校验缓存的行为。

## 停止曲线检查与调整

直接二次衰减的 `2τ` 方案虽然在终点的振幅和速度均为零，但会明显缩短中段，因此本次改为更保守的连接曲线。

令 `h = ln(2) × τ`：

- `0 ≤ t ≤ h`：`A(t) = A0 × exp(−t/τ)`，保留原来的前半振幅衰减。
- `t > h`：`A(t) = A0/2 × max(0, 1 − (t−h)/(2τ))²`。
- 在 `h` 处振幅及其导数连续；在 `(ln(2)+2)τ ≈ 2.693τ` 时振幅及其导数为零。

| 已用时间 | 原指数 | 先前直接二次方案 | 本次连接曲线 |
| --- | ---: | ---: | ---: |
| 0.5τ | 60.7% | 56.3% | 60.7% |
| 1τ | 36.8% | 25.0% | 35.8% |
| 1.5τ | 22.3% | 6.3% | 17.8% |
| 2τ | 13.5% | 0 | 6.0% |
| 2.693τ | 6.8% | 0 | 0 |

Up/Down 共用同一个进度，stop→idle 不重启计时，重新移动从当前振幅恢复。原有 stop 授权与未知/攻击/技能/跳跃取消规则继续生效。释放频率保持固定。

测试覆盖 τ=0.015/0.2/0.3/0.5/0.7/1/3 秒、不同振幅、频率、相位与帧率，检查单调性、连接点速度、归零点角度与角速度，以及 stop→idle 和再次起步。当前预设 τ 为 0.2–1 秒，对应有效推进时间约 0.539–2.693 秒。按预设最大振幅计算，60fps 最后一个归零间隔开始前的振幅上界最大约 0.0434°；20fps 最坏约 0.391°。这是数学上界，非实机测量。

历史两份 capture 共提取了 16 个停止标记窗口，用捕获的初始振幅、频率和预设 τ 做离线曲线对照。每步时间按 Runtime 的 50ms 上限估算，避免把菜单/暂停长间隔当作动画时长；这不是新 DLL 的实机回放结果。3 个约 2.94–2.99 秒的冲刺停止窗口会在自定义摆动约 2.693 秒归零后，继续播放约 0.25–0.29 秒原生停止动画。不能把“有限时长且连续归零”解释为“所有角色必须到 stop clip 结束才归零”。

很小的 τ 仍意味着很快的收尾。例如 τ=0.015 秒的总释放时间只有约 40ms，在低帧率下仍可能表现为一两帧结束；当前使用中的预设没有这么小的 τ。其他角色的实际停止动画长短与最终观感尚未实机验证。

## 后续：进入 sprint 后的频率迟滞

用户明确延迟发生在 dash 结束、已进入 sprint 之后。当前角色 `frequency_tau_sec=1`，频率包络补齐 63% 的目标差值需约 1 秒，95% 需约 3 秒；这是代码和参数可直接确认的迟滞来源。历史 dash 片段的无写入窗口不能解释用户指出的这段现象。

本次最终只修改步态切换的频率平滑：新进入已支持的 locomotion gait 时，以不大于 0.10 秒的内部时间常数追踪该步态的配置/有效缓存目标，补齐约 95% 差值后恢复普通 `frequency_tau_sec`。停止、跳跃和不支持动画后重新进入 locomotion 也适用。后续同一步态的频率拟合微调继续使用配置平滑。没有修改振幅包络、落地控制器、dash 白名单、频率测量算法或 PLL ±20% 总限速。

新增测试覆盖四种 locomotion gait 的有向切换、20/30/60/144fps、相位连续性、已有更快用户配置、停止频率冻结和跳跃后重新进入 sprint 的状态重置。`verify.bat` 最终为 **427 passed，0 failed**，完整构建通过，日志为 `verify_gait_frequency_transition.log`。

以上验证了频率包络的响应，没有把它等同于实机中的最终摆动速度。实际相位速度还含 PLL 修正；安装后应短测 run→sprint 和落地后 sprint，同时比较 `freq_env_hz` 与 `phase_rad` 推导出的实际频率。本次仍未安装。
